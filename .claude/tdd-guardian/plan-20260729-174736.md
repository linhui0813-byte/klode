## Risks & Assumptions
- **Gate tests are content-coupled to kb-01, not merely path-coupled.** `tests/test_gate.py` asserts on dimension `worldbuilding`, count thresholds (`≥5` criteria, panel `>10`), and a copyrighted grounding phrase ("The status quo does not need world building"). WI-2 therefore cannot be a pure path swap — the fixture must reproduce an equivalent non-copyrighted structure and the assertions must be rewritten to it. This is the largest hidden effort in the plan.
- **Facade stability (`lode/lib/__init__.py`).** The plan is designed to require **zero** `__all__` changes: identity rides on the already-exported `Config`; registry/discovery live in an internal `registry.py` consumed by adapters. If any implementer instead exports a new symbol from the facade, `tests/test_public_api.py` (which pins the exported contract) and the `gate`→`lib` public-API boundary become live risks and the change must be justified.
- **`gate`→`lib` boundary.** `gate` must keep importing only the `lib` facade. None of these work items give `gate` a reason to touch internals; registry/discovery are adapter/CLI/MCP concerns, so the boundary is preserved. (Note: `tests/test_layering.py` as written enforces the *lib-internal* adapter boundary — that `registry.py` and the new commands do not import `cli`/`mcp_server` — which WI-3/4/5 must respect; the `gate`-side discipline is enforced by `gate`'s facade-only imports and `test_public_api.py`.)
- **`ConfigError` vs. `RegistryError`.** WI-3 must decide whether the registry raises `ConfigError` directly or a subclass. Subclassing keeps the CLI's existing `except ConfigError` handler working (exit code 2) with no adapter change; a sibling exception type would need the handler widened. Recommend subclassing.
- **Registry validation timing.** Eager-validate-every-entry (fail fast, but one bad KB breaks `lode kbs` entirely) vs. validate-on-resolve (discovery still lists a broken KB). WI-3 must pick and document; discovery UX (WI-4/5) depends on the choice. Recommend lazy/on-resolve validation for discovery with a per-entry status, so one broken KB does not blank the whole catalog.
- **`id` uniqueness across a manifest** must be enforced; duplicate ids are a `ConfigError`. Slug charset and normalization rules (WI-1) and the server-name derivation (WI-6) must share one definition to avoid drift.
- **Zero new dependencies** holds for all five changes (all reachable with `tomllib`/`pathlib`); the only optional dep in the repo (`minicheck`, behind `check --entail`) is untouched.
- **Test count.** "153 passing" is a baseline; new WIs add tests. The invariant is that no existing test regresses; the count only grows. WI-2 may *convert* currently-skipped gate assertions into actually-executing ones (the absolute-path `skipUnless` silently skips off the author's machine today).
- **Assumption:** `~/.lode/registry.toml` and project-level manifest locations are new conventions this plan introduces; no existing file or env var (`LODLIB_CONFIG`) is repurposed. The MCP server keeps its `--config`/`$LODLIB_CONFIG`/nearest-`library.toml` resolution unchanged.
- **Assumption:** `eval/*.py` require no change (verified: they build their own tmp fixture and carry no `corpus/`/absolute reference); the plan documents this rather than modifying `eval/`.

## Deferred / Out of Scope
- Physically moving `corpus/kb-01-storycraft` into its own repository/package. Only the testable residue (fixture + repointed references in WI-2) is in scope; the extraction/publishing of the real KB is not a TDD deliverable.
- A `lode kbs` mode that *recommends* or *auto-routes* a KB to a query. The discovery surface is explicitly passive (list + describe only) per changes #4a/#4b; any ranking/routing is a separate future feature.
- Registry *mutation* commands (`lode kbs add/remove/init`, writing manifests). This plan covers reading/loading/precedence and read-only discovery only.
- Multi-KB serving from a single MCP process (one server still serves one KB per `--config`); WI-6 only ensures distinct *names* across separate per-KB server instances.
- Changes to the citation-rot linter, BM25 retrieval, normalize/ingest pipelines, or the `entail` optional path.
- Migrating existing production `library.toml` files to add identity keys (backward-compat means they keep working with derived defaults; authored identity is opt-in).
- Non-TOML registry formats (JSON/YAML/env-based discovery) and network-hosted registries.
