**Verified:** python3 -m unittest tests.test_pool (8 passed); tests.test_layering (pool.py imports no adapter, 4 passed)

- **Description**: Add a `KBPool` abstraction (new `lode/lib/pool.py`, or a section within `mcp_server.py` — either is acceptable so long as it imports no adapter). It is built from `registry.load(...)` and maps a registry `id` to its lazily-loaded, cached `Config` via `registry.resolve(kb)`. This is the addressing substrate every later work item routes through. No `handle()` or tool changes in this item.
- **Acceptance criteria**:
  - [ ] `KBPool` is constructed from a `tuple[KB, ...]` (the output of `registry.load`), with no eager `Config` loading at construction time.
  - [ ] `pool.ids()` returns exactly the registered ids in a stable (sorted) order, matching the registry.
  - [ ] `pool.config(kb_id)` returns the KB's `Config`; a second call for the same id returns the *same cached object* (lazy load + memoize).
  - [ ] `pool.config(unknown_id)` raises a typed error whose message names the unknown id AND lists every valid id.
  - [ ] A pool built over a registry containing one broken KB entry constructs successfully; `pool.config(good_id)` works and `pool.config(broken_id)` raises `RegistryError` naming that id (laziness preserves "one bad entry never disables the server").
  - [ ] A single-entry pool exposes that sole id as the *default*; a multi-entry pool exposes *no* default (a `None`/sentinel).
  - [ ] An empty registry yields an empty pool (`ids() == ()`), no default.
  - [ ] Zero new imports beyond stdlib (`tomllib`/`pathlib`) and existing `lode.lib` modules (`registry`, `config`).
- **Required tests**:
  - `ids()` over a 2-KB registry fixture equals the exact sorted id tuple — assertion level: Level 1 (output verification)
  - `config(id)` returns a `Config` whose `.id`/`.name` match the addressed KB — assertion level: Level 1 (output verification)
  - Second `config(id)` returns the identical object instance (cache) — assertion level: Level 4 (state verification of the cache)
  - `config(unknown)` raises; asserted error message contains the unknown id and every valid id — assertion level: Level 1 (output verification of the raised error)
  - Pool over a registry with one broken entry: constructs, `config(good)` works, `config(broken)` raises naming it — assertion level: Level 1 (output) / guard-clause category
  - Single-entry pool reports its default id; multi-entry reports no default — assertion level: Level 1 (output verification)
  - Empty registry → empty pool, no default — assertion level: Level 1 (boundary case)

## Risks & Assumptions
- **`handle` signature migration touches exactly two existing tests.** Changing `handle(cfg, msg)` → `handle(pool, msg)` breaks the two sites that pass a `Config`: `tests/test_mcp_schema.py:60` (`test_initialize_reports_lode`) and `tests/test_discovery.py:126` (`test_malformed_registry_is_in_protocol_error_not_a_crash`). Both must be migrated to a single-KB pool. This is a signature migration, not a behavior change; "all 200 green" is met only after migrating these two. `McpCharacterization`, `test_lodlib`, and the `_tool_list_kbs(cfg, …)` direct calls are unaffected because they never call `handle()`.
- **Provenance is ALWAYS tagged on grounded results (requester decision).** Every grounding-tool result names its KB with a `[kb-id]` prefix in single-KB and multiplex modes alike. This INTENTIONALLY changes today's single-KB grounding output (it gains the tag), so the "byte-identical to today" guarantee now applies to the **discovery** tools only; grounding-tool equivalence is measured as `[kb-id]` tag + prior output. Discovery output stays untagged for a single KB and tags per-KB only on fan-out (discovery results are navigational pointers, not grounded citations) — if uniform discovery tagging is also wanted, that is a further change to flag.
- **`kb`-required is enforced at runtime, not in JSON-schema `required`.** To preserve single-KB ergonomics and keep `consult_dimension.required == {"dimension"}`, `kb` is never placed in a `required` array; the router returns a clean in-protocol error when `kb` is missing with >1 KB. Risk: a client that inspects only JSON-schema `required` will not force `kb` — acceptable, since the server answers with an explicit id-listing error.
- **Do not touch `query.py` / `console.py`.** They are already KB-agnostic (they take a `cfg`). Any proposal to modify them to "pass a pool" is a design smell and must be flagged — all multiplexing belongs in the router.
- **Zero new dependencies.** Only stdlib (`tomllib`/`pathlib`) plus existing `lode.lib` modules. Any added package violates the core promise.
- **Registry `id` is the addressing key.** Grounding/discovery `kb` values are the registry manifest ids surfaced by `list_kbs`/`pool.ids()`. A `--config` pool uses the KB's own `Config.id` as its sole entry id. A manifest may alias a KB under a different registry id (allowed, per `registry.py`).
- **`list_kbs` reads the registry independently of the pool.** In legacy `--config` mode, `list_kbs` may show a registry that differs from (or omits) the single served KB — unchanged from today, by design.
- **Lazy broken-KB handling.** A broken KB surfaces only when addressed (grounding → in-protocol error) or as a tagged block (fan-out), never at pool construction, so one bad KB never disables the server (consistent with `registry.describe` laziness and the existing `list_kbs` broken-entry test).
- **Fan-out is bounded, not richly paginated.** A fixed cap + deterministic sorted-id order + truncation annotation is the mechanism; the agent narrows by addressing omitted KBs explicitly.
- **Deployment repointing (ops, not code).** The running server is registered via `claude mcp add lode -- lode-mcp --config <one kb>`; multiplex requires repointing that registration to `--registry <path>`. Out of scope for this code change; call it out at rollout.

## Deferred / Out of Scope
- **Auto-routing / relevance ranking of KBs to a query.** Explicitly excluded — the server never infers which KB answers a query; the only cross-KB behavior is explicit fan-out on discovery tools.
- **New tools.** This is parameterization of the existing 8, not new surface; the tool count stays 8.
- **Rich fan-out pagination** (offset/cursor/page tokens) beyond a cap + truncation notice.
- **Cross-KB merging/dedup/ranking of fan-out results.** Results stay per-KB, `[kb-id]`-tagged, and unranked.
- **`$LODLIB_REGISTRY` env-var parity with `$LODLIB_CONFIG`.** Not requested; `--registry` is the activation path and legacy resolution is unchanged.
- **Hot-reload of the registry** while the server is running (the pool is built once at startup).
- **Any change to `query.py` / `console.py`.**
- **MCP client re-registration / deployment change** (operational task, not code).
